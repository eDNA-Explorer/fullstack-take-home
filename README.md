# eDNA Explorer Take-Home Challenge

This project consists of a data pipeline (Dagster) and a dashboard (Next.js). The pipeline processes FASTQ genomic sequencing data and outputs Parquet files that the dashboard consumes via tRPC.

This challenge is deliberately open-ended. We assume you will use coding agents — that means the bar for "code that runs" is low, and our evaluation focuses on the engineering decisions you make on top of that. **Push the system. Measure it. Defend your choices.**

## What We're Looking For

|                          | Weight     | What we're looking for                                                        |
| ------------------------ | ---------- | ----------------------------------------------------------------------------- |
| Architecture & taste     | High       | Sensible choices, defended honestly. Shape of solution > volume of code.      |
| Measurement              | High       | Real numbers on real hardware for real workloads. Benchmarks beat assertions. |
| Performance              | High       | Throughput, memory, latency. Not "it works" — "it works at N."                |

## Getting Started

### Prerequisites

This project uses [mise](https://mise.jdx.dev/) to manage tool versions (this is optional and just for your convenience). Install mise and run:

```bash
mise install
```

This will install the correct versions of:
- **Bun** - JavaScript runtime for the dashboard
- **Node.js 22** - Required for some tooling

### Data Pipeline

```bash
cd data-pipeline
docker-compose up
```

Dagster UI will be available at http://localhost:3000

### Dashboard

```bash
cd dashboard
bun install
bun dev
```

Dashboard will be available at http://localhost:3001

## Challenge 1: High-Throughput Data Pipeline

The starter pipeline has three stubbed assets. Replace them with a working pipeline, then make it fast.

### What the pipeline must produce

Three Parquet outputs in `data-pipeline/output/`:

- **`sample_list`** — One row per sample, with at least the sample identifier and the paths to its forward/reverse FASTQ files.
- **`sequence_counts.parquet`** — Unique sequences per sample with their read counts. At minimum: `sample_id`, `sequence`, `total_reads`.
- **`sample_stats.parquet`** — Per-sample quality metrics. At minimum: read counts, mean quality, %Q20, %Q30. GC content and length stats are welcome.

The exact column shapes are up to you. So is tool choice: `seqkit`, `pyfastx`, BioPython, scikit-bio, `fastp`, DuckDB, Polars streaming, Dagster graph-backed assets, partitions, custom Rust/C extensions — pick what you can defend.

### The actual challenge: scale it

**The 8 included samples are a smoke test, not the workload.** Generate, download, or synthesize a much larger dataset and run your pipeline against it. Some options:

- Replicate and perturb the starter samples to build a larger corpus.
- Pull real reads from public archives (SRA, ENA, MGnify).
- Synthesize reads with `wgsim`, `dwgsim`, or `art_illumina`.
- Simulate metagenomic communities with configurable diversity (`iss` / InSilicoSeq, CAMISIM). Community complexity is a separate stress axis from raw read volume — both are worth exploring.

How big? Big enough that your design decisions show up in the numbers. Going from 8 samples to 800 should look interesting; 8,000 should be informative; 80,000 should hurt somewhere, and you should be able to explain where.

Your choice of dataset generation strategy — and what you decided not to use — is itself something we'll ask about.

### What we want you to measure and report

Include a `BENCHMARKS.md` reporting:

- **Wall time** — Full pipeline run, end to end, on at least two dataset sizes.
- **Throughput** — Reads/sec and/or MB/sec, both per asset and overall.
- **Peak memory** — RSS per asset, measured (not estimated). Tools: `/usr/bin/time -v`, `psutil`, `memray`, etc.
- **Scaling curve** — How wall time and memory move as you go 10x / 100x / 1000x the starter dataset.
- **What broke first** — When you pushed it, what gave out? CPU? Memory? Disk? gzip? Python interpreter overhead? Parquet writes?
- **Hardware** — CPU model, core count, RAM, disk type. Numbers without hardware context are not useful.

### Questions we will ask in follow-up

- How many reads/sec can you sustain on a 60-second budget? A 10-minute budget?
- Where is the bottleneck — CPU, memory, disk I/O, gzip decompression, Python overhead, Parquet serialization?
- What changes between 10x and 100x? Does anything you did stop working?
- Does peak memory stay flat as the dataset grows, or does it climb? Why?
- What tool choices did you try and reject, and why?

### Compatibility note

The dashboard reads Parquet via `parquetjs-lite`, which has limited encoding support and currently requires `use_dictionary=False` and `version="1.0"` on the writer side. That constraint is itself a legitimate optimization target — swapping in a Parquet reader with modern encoding support is a reasonable thing to consider and discuss.

> A small, correct, well-measured pipeline that reports "I hit X GB RAM at Y samples and here's why" beats a sprawling one with no numbers.

## Challenge 2: Performant, Creative Visualization

You've run the pipeline over hundreds of samples and millions of sequences. A researcher opens the dashboard.

- What do they see in the first five seconds that's actually useful?
- What's drillable?
- What makes them say "oh, that's interesting" instead of "ok, a bar chart"?

The current dashboard is stubbed. Replace it.

### What we want to see

- **A point of view.** You pick which views matter and defend them. Generic dashboards are easy to generate; opinionated ones are not.
- **Visualizations that fit the data.** Examples (not requirements): quality score distributions, GC content vs. read length scatter, sequence rank-abundance or rarefaction curves, sample-to-sample similarity, k-mer composition signatures (sample clustering without taxonomic assignment), contamination indicators. Pick views that make biological sense and that you can explain.
- **Performance at scale.** Server-side aggregation vs. shipping raw rows to the client. Streaming, pagination, virtualization. Memoization, web workers, GPU rendering, canvas/WebGL when appropriate. What blocks initial load — and what doesn't.
- **At least one view that handles 100K+ rows gracefully.** TanStack Virtual, windowed rendering, server-side search — examples, not requirements.

### What we want you to measure and report

Add a section to `BENCHMARKS.md` (or a separate `DASHBOARD_BENCHMARKS.md`) with:

- **Time to interactive** on both the starter dataset and your scaled-up dataset.
- **Bundle size**, with a breakdown of the biggest contributors.
- **Frame rate / interaction latency** on your heaviest view. Chrome DevTools Performance screenshots are fine.
- **Network payload** for the main page and your heaviest query.
- **What you'd do next** with another day, and why you didn't do it now.

### Questions we will ask in follow-up

- Why these views?
- Where does it fall over — 10K rows? 1M? 100M?
- What computation lives on the server vs. the client, and why?
- How does data get from Parquet to pixels? How many copies, parses, and re-renders along the way?
- What suffers first on a 4-year-old laptop on hotel wifi?

## Technical Notes

- The dashboard uses `parquetjs-lite`, which has limited encoding support; Parquet files must currently be written with `use_dictionary=False` and `version="1.0"` for compatibility. (Treat this as a constraint you can replace, not a permanent fact.)
- The data pipeline outputs are synced via Docker volume to `data-pipeline/output/`.
- The starter assets in `data-pipeline/src/data_pipeline/defs/` are intentionally stubbed. Replace them; don't preserve them.
- Any generated or downloaded larger dataset **must not be committed**. Add it to `.gitignore` and describe how you sourced or generated it in your writeup so we can reproduce.
